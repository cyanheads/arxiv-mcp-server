# 1.4.0 — 2026-07-27

## Added

- **`arxiv_read_paper`** gains a third content-fallback rung: when neither `arxiv.org/html` nor ar5iv has an HTML render, the service downloads the PDF and extracts text via the framework's `pdfParser` (`unpdf`). Response `source` gains `pdf_text`; `content` on that rung is plain text — prose is reliable, but math, tables, and heading structure flatten. [#23](https://github.com/cyanheads/arxiv-mcp-server/issues/23)
- **`max_characters`** on `arxiv_read_paper` accepts `null` to return the entire cleaned paper body in one call. The 100,000 default is unchanged; whole-paper reads can exceed a client's tool-result size cap, so the bounded default plus `start`-based paging stays the recommended path. [#24](https://github.com/cyanheads/arxiv-mcp-server/issues/24)

## Changed

- **`arxiv_read_paper`'s content-fallback chain no longer terminates on an ar5iv 5xx, network error, or timeout.** The failure is held and re-raised only if the new PDF rung also fails to produce usable text — a third-party ar5iv outage now narrows coverage instead of failing the call. [#38](https://github.com/cyanheads/arxiv-mcp-server/issues/38)

## Dependencies

- `unpdf` added `^1.6.2` — lazy-loaded peer of the framework's `pdfParser`, used by the new PDF-text extraction rung.

## Migration

`arxiv_read_paper`'s `errors[]` contract replaces `html_unavailable` with two reasons:

| Before | After |
|:-------|:------|
| `html_unavailable` — no HTML render on either source | `content_unavailable` — no HTML render and arXiv served no PDF |
| (not distinguished) | `pdf_extraction_failed` — PDF has no text layer (scanned/image-only) |

Clients keying on `error.data.reason === 'html_unavailable'` must check for both new reasons instead.

# 1.2.4 — 2026-05-22

## Fixed

- **`arxiv_search` against the mirror** now resolves queries that mix bare terms with `all:` expansions or user-typed parentheses ([#13](https://github.com/cyanheads/arxiv-mcp-server/issues/13)). The translator emitted `"language" (title:"automated" OR …)` for `language all:automated` and relied on FTS5 implicit-AND, which only spans bare phrases — anything crossing a paren boundary failed with `fts5: syntax error near ":"`. New `joinFtsParts` walks the emitted parts and inserts an explicit `AND` whenever adjacency crosses a parenthesized form (literal `(`/`)` tokens, single-string `all:` expansions, or user groups). Bare-phrase and bare-column-qualifier adjacency continue to use implicit-AND.
- **`ArxivService.searchMirror`** wraps `store.search()` and rethrows any `Error` whose message matches `/^fts5:/` as `validationError` with `data.reason === 'unsupported_query_syntax'`, `data.query`, `data.matchExpr`, and the contract `recovery` hint. Defense-in-depth against future translator regressions — callers see an actionable validation error instead of a raw SQLite engine string. Non-FTS5 errors propagate untouched.
- **`arxiv_search` error contract** declares `unsupported_query_syntax` so the recovery hint ("Add an explicit `AND` or `OR` between adjacent terms and parenthesized groups, then retry.") is the single source of truth for both the service's runtime throw and the LLM-facing tool description.

## Notes

- `cat:` extraction inside parentheses ([#14](https://github.com/cyanheads/arxiv-mcp-server/issues/14)) remains an open translator bug — the new defense-in-depth catch makes its symptom land as `validationError` instead of raw `SQLiteError`, but the underlying empty-group emission is not addressed here.
